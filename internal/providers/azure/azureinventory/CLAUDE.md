# CLAUDE.md — `internal/providers/azure/azureinventory/`

Azure SDK inventory: the extractor that derives the Azure coverage denominator from the pinned SDK source, its refs, its pairing resolver and its pins. Core contract and pairing walk: `internal/sdkinv/CLAUDE.md`.

## Cache layout

- `azure@<sha>/repo/sdk/resourcemanager/<rp>/arm<rp>/*.go` — every non-test file except fakes and
  `client_factory.go` (`keepARMFile`, `KeepID` `arm-go-sources-v3`). `models_serde.go` is kept: it is
  the only place the SDK states JSON names. Filter anchors on `sdk/resourcemanager/` — the monorepo
  also ships `profile/*/resourcemanager` copies. HEAD holds one major per module dir, so no version picking.

## Pins (`pins.go`)

- `SDKRef` = azure-sdk-for-go commit SHA (no monorepo tag). The policy is HEAD only: pinning per
  `go.mod` deletes rows HEAD still lists. `absentModules` warns for each arm module the binary links
  (`debug.ReadBuildInfo`) that HEAD no longer holds (armappplatform), so a retired module's types
  are named instead of vanishing.

## Extractor (`module.go`, `extract.go`, `refs.go`)

Model-first: each module is parsed with `go/parser` (parallel, ~1 s for the whole tree).
There are **no spelling lists** — removed, do not recreate: `singletonIDs` (`default`/`current`),
`armOwnModules`, `lowerFirst`, the `SubResource`/`Reference` suffixes and the keyvault/encryptionkey
URI allow-list. The declared vocabulary is ARM's scope names
(`scopeNames`) and the ARM envelope fields (`ID`, `Type`, `SystemData`). The generator's own
conventions that remain: a builder's op name is its method name less `CreateRequest`, and an
`…ID`/`…IDs`/`…URI`/`…URL` Go name is the generator's initialism for an identifier. Every rule
below has a case in `testdata/.../armwidgets` (generated by a scratch script; comments there name
the rule) — each of 50 was mutation-checked red (2026-09-28) but one: `b.paged || paged` (a builder
reached by both a pager and a plain method; the generator emits one builder per method).

- **Ops.** A builder is any client method returning `*policy.Request`, read for its literal
  `urlPath` and `http.Method<Verb>`. Every exported client method is a source op, followed through
  its `client.x(...)` calls transitively to the builder and the response decoder it reaches — no
  `Begin`/`New…Pager` name grammar. No builder reached → drop `no-request-builder`; a builder with
  no literal path → `no-request-path`. `Paged` = an exported method returning `*runtime.Pager`
  reaches it.
- **Response shape** (`shapeOf`). The decoder's `&result.<F>` field, looked up on its response
  struct (embedded model, or the older `<X>Array []*X` field). A slice is a list. A model with exactly
  one slice of models and no `ID` of its own is a list result whatever the field is named and whatever
  else it holds (attestation's `SystemData`, billing's `Summary`); among several slices, the one of
  identified models wins (savings plans beside summaries). Anything else is one model
  (`VirtualMachineInstanceView`: several slices; hybridcompute validation details: an `ID`).
  `XClassification` resolves through its interface's one method `GetX() *X`.
- **Lister vs item.** A GET on a static-final path lists, except a non-paged GET answering one
  model: that is an instance read (`…/{vm}/instanceView`) and goes to Other — unless the
  collection has item PUT/PATCH/DELETE and no other lister. Then it is promoted to the lister
  (`single-answer-lister`): the SDK types `managementpartner` `partners` and `webapps`
  `ListRelayServiceConnections`/`ListPremierAddOns` as one entity, and dropping them lost five
  writable resources. Paged is a list whatever the page's shape.
- **Instance ids** (`instanceIDs`). A static S after a static C is an id when S is not itself
  listed and either the SDK also spells `C/{param}` there (`billingAccounts/default` beside
  `billingAccounts/{name}`), or it addresses `C/S` as an instance (PUT/PATCH/DELETE, or a GET
  answering one model) while C is not one (`sites/{n}/config/web`, `blobServices/default`,
  `sqlVulnerabilityAssessments/default`). A static only POST addresses is an action, never a
  sibling id (`servers/checkNameAvailability` beside `servers/{name}`; it once put `item:POST` on
  11 collections). The C guard keeps `runbooks/{r}/draft/testJob`: draft is a
  singleton, testJob is not its id. Ids apply to every longer path through the prefix
  (`config/web/snapshots` keys `sites/config/snapshots`). Only segments after the namespace qualify.
- **Namespace** (`split`). After the last `providers` whose successor is static (the generic
  `…/providers/{resourceProviderNamespace}/features` form otherwise loses the real namespace; the
  trailing pair strips since `providers` is a scope name). No `providers` segment → ARM's own
  `microsoft.resources` (any module: armdeployments' resource-group paths joined). A parameter
  namespace, or no static left after the scopes (`/{resourceId}` by-id ops), → Other plus an
  info diagnostic.
- **Key** = namespace + statics after scope pairs and ids strip. **Parent** = the key up to the
  innermost static followed by an id, so it agrees with Depth (cutting only the last static named
  `runbooks/draft/testjob`, no collection). 63 live parents are still not keys: their collection
  has no lister (depth>0 with no candidate parent is legal).
- **Scope** (`scopeOf`) from the whole template; `extension` is decided on the prefix before the
  namespace (`{scope}` first, or a `providers/{p}` pair). A collection every lister of which
  reaches through `locations/{l}` carries `scope-pair:locations` (ARM keeps it in the type name;
  `RegistryKey` puts it back).
- **Class.** Item PUT/PATCH/DELETE → resource `item-write`. GET-only item + (child or
  subscription/resource-group scope) + ARM envelope on the element (`SystemData`, or `ID`+`Type`)
  + not reached only through `locations/{l}` → resource `arm-envelope`. Every part is
  load-bearing: envelope alone admits `microsoft.authorization/provideroperations`, and without
  the location gate 56 regional catalogs (`servicefabric/managedclusterversions`, oracle
  `giversions`, `sql/timezones`) counted as resources. GET-only otherwise → catalog; no item path
  → non-resource.
- **Alternate listers.** A lister with no item path whose element a same-module writing entry
  lists folds into it (`alternate-lister`: sql replication links, billing reservations).

- **Parse errors.** A module with a file `go/parser` rejects is skipped with a `warn` diagnostic;
  the rest of the universe still extracts. `disco coverage` prints a per-provider warning count
  (`--verbose` lists them), so a skipped module is never silent.

### Refs (`refs.go`)

By shape on the list element, at most `refDepth` (3) below it, named by JSON names from
`models_serde.go` (`populate(objectMap, "<json>", x.F)` in MarshalJSON, `case "<json>"` in
UnmarshalJSON — polymorphic models skip fields in one of them) or the older layout's struct tags.
A field with no JSON name is skipped. Refs: a sub-resource struct (`ID` + at most one field),
an `…ID`/`…IDs` string, and a `…URI`/`…URL` string only beside a sub-resource sibling (a key URL
next to its source vault). A larger struct holding an ID (`ImageReference`) is walked, not a ref.
Not refs by design: `managedBy`, and a key vault URI with no vault sibling — no structural fact
marks them; a second source (azure-rest-api-specs `x-ms-arm-id`) is the follow-up.

### Accepted residuals (2026-09-28, pin f3847e89)

3395 candidates (2478 resource). Not candidates: singleton reads
that were never listers (`instanceview`, `config/web`, `…/status`) and the location-only regional
catalogs above. Now resources: addressed singletons (`web/sites/config`,
`…/basicpublishingcredentialspolicies`, `apimanagement/service/portalsettings`, mysql/postgresql
`servers/administrators`). Known misreads, all tolerated because no structural fact separates them:

- The location gate also demotes a few real read-only resources to catalog:
  `vmwarecloudsimple/privateclouds` and its children, `dataprotection`/`recoveryservices`
  `deletedvaults`, oracle `dnsprivateviews`/`dnsprivatezones`, `iotsecurity/devicegroups/devices`.
- Envelope catalogs outside locations stay resources (securityinsights content templates,
  compute `vmextension/types/versions` under a publisher).
- `shapeOf` reads a few non-resource responses wrongly (`ServiceTagsListResult` carries an `ID`,
  so it is one model; some single models with one slice read as lists). None is a resource row.
- Refs: the `…URI`/`…URL` sibling rule also admits `targetUrl`/`blobUri` beside a sub-resource,
  and a `…GUID` field matches the `ID` suffix. Refs are hints; precision is not the goal.
- `parentEnd` matches the innermost static by name, so a repeated static name can pick the
  wrong one. None seen live.
- `resources/` and `solutions/` each hold an `armmanagedapplications` module; all 18 of
  resources/' universe op names also exist in solutions/ (31), on the same candidates
  (`microsoft.solutions/{applications,applicationdefinitions,operations}`). Module keys are therefore `<rp>/<armX>` (`ImportKey`, `OpKey`), so an import
  anchors only its own module's ops; labels keep `armX:`, and `LabelModule` maps a key back for
  `moduleAbsent`. A label alone still cannot tell the two apart; it resolves through the
  file's import. Live effect at the fix: zero pairing change (the solutions scanner already
  anchored correctly), 14 sdk-skew messages now print the `<rp>/<armX>` key. Fixture:
  `gadgetry/armwidgets` beside `widgets/armwidgets`.
- `applicationgatewaywafdynamicmanifests/dafault` (sic) is read as an id: the structural rule
  caught a misspelled singleton a word list never could.

## Pairing resolver (`resolver.go`)

- sdk-skew is expected and runs both ways, because `SDKRef` is monorepo HEAD, not the
  go.mod majors. An op newer than the snapshot → bump the pin. An op **deleted upstream**
  (armcompute `CloudServices*`, the whole armappplatform module) → bumping moves further away;
  the fix is a `go.mod` major bump plus retiring the scanner. `TestScannerOpLabelsResolve` logs
  the imported `arm` modules the snapshot no longer holds. Never pin Azure per `go.mod`.
- A receiver binds from `armX.New<Y>Client(`, a client-factory `cf.New<Y>Client()`, a
  `*armX.<Y>Client` parameter or struct field, or a package-local interface seam whose method
  signatures mention `armX.<Y>Client…Response/Options`. `TypeOwner` takes the module's known
  clients from the universe and binds the **longest** that prefixes the type at a word boundary
  (`ClientGroupsClientListResponse` is not the bare `Client`'s); a type no known client prefixes
  binds nothing. An unbound pager resolves only when exactly one imported client has that op.
  Any `List*` on a bound client anchors even when the pin lacks it (skew surfaces in Walk).
- Label form is `armX:<Y>.<Op>` with the `Client` suffix dropped and bare `Client` kept
  (`armredis:Client.ListBySubscription`). `LooseLabelGrammar` (Azure only) catches the near miss
  `arm<module>:<Op>` with the `Client.` dropped. AWS's decorated labels
  (`amp:ListWorkspaces(extended)`) are deliberate: do not give AWS a loose grammar.

## Spec-annotated refs (`x-ms-arm-id`): measured 2026-10-01, deferred

The idea: read `format: arm-id` / `x-ms-arm-id-details` from azure-rest-api-specs to add refs the
shape rule (`refs.go`) cannot see. Measured against the live universe (SDK `f3847e89`, specs
`e7902d1f`): each resource candidate's list path is joined to its spec at the SDK client's own
`api-version`, and the 200 `value[]` items are walked.

- **Cost.** The specs tarball is 214 MB. `resource-manager` JSON for every API version is 819 MB
  (14,198 files). The 328 version directories the SDK actually uses are 64 MB, plus 0.2 MB of
  `common-types`. It would add a fetch source and a pin.
- **Version skew.** Every one of the 10 sampled modules is TypeSpec, pinned to a spec commit 2
  weeks to 8 months behind specs HEAD. Joining to the latest spec version instead of the SDK's put
  55% of joined candidates (123 of 273 modules) on a different version. The total barely moved,
  but the ref sets differed on 22 candidates, so the version must be picked per module.
- **Coverage.** 2,384 of 2,478 resource candidates join. 74 do not: 71 are retired RPs absent from
  specs HEAD (storsimple, videoanalyzers, blockchain, …), 3 are version-folder misses. 20 more
  have no `value`. Only 352 carry any annotation. Of 1,012 annotated paths, 667 are already shape
  refs (a ref struct at `p` counts for an annotated `p.id`). Of the 345 new paths, 218 lie below
  `refDepth`; only 127 are within it, on 64 candidates (2.6%). 62 of those 127 come from
  discriminator subtypes, which the shape rule never walks (`model()` maps `XClassification` to
  its base).
- **Cannot replace the shape rule.** 4,713 of the 5,380 shape refs on joined candidates (88%)
  carry no annotation. `additionalProperties` maps (the UAMI identity map) carry none and have no
  dotted path on either side.
- **Requirements for any build.** Resolve `common-types` (`Resource.id` and the identity and
  private-endpoint types live there). Skip the element's own `id`, as `walkRefs` does. Walk
  discriminator subtypes. Exclude the spec repo's test fixtures (`.github/**/test`,
  `eng/tools/*/test`). A first measurement missed `common-types` and subtypes and joined to the
  latest version; it reported 83 new refs, against 127 after correction.

Defer: about 125 within-depth refs on under 3% of candidates do not pay for a 64–214 MB source
plus per-module version selection. Revisit if annotation coverage grows. Separately, walking
discriminator subtypes in the shape rule itself would recover some of the 62 subtype refs with
no new source.
